## 브라우저 실사용 QA (Sonnet 담당 영역 — UI/UX 실동작 검증)

Node 하네스는 DOM을 스텁으로 흘려보내 로직만 검증했을 뿐, 실제 클릭·렌더링은 이번에 처음 확인했다.
클로드인크롬으로 배포 사이트를 직접 조작하며 Phase 1→2→3→4 전 구간을 실제로 눌러보고, 그 과정에서 실사용 버그 2건을 새로 발견·수정했다.

1. **함수별 주석 발췌가 이전 함수의 주석까지 끌어옴** — `attachComments()`가 `f.startLine-6` 고정 lookback만 쓰고 이전 함수의 `endLine`을 고려하지 않아서, 함수 간격이 6줄보다 좁으면 이전 함수 끝의 주석이 다음 함수 설명에 섞였다.
   실측: 샘플 코드에서 `CheckGearStatus()` 상세 패널에 `CheckSeatBeltStatus()`의 "벨트 미착용 시 출력 제한" 주석이 함께 표시됨을 화면에서 확인.
   수정: 정렬된 함수 목록에서 `직전 함수.endLine + 1` 을 하한선으로 추가 — 함수 경계를 넘지 않도록 clamp.
2. **짧은 키워드(3자 이하)가 다른 단어 안에 우연히 포함되는 오탐** — `classify()`/`describeFunc()`가 `문자열.includes(키워드)` 부분일치를 썼는데, `'ain'`(센서/신호 카테고리, `Make_AIN` 대응용)이 `'maintenance'`(유지보수) 안에 그대로 포함되어 있어 `Check_Maintenance_Info()`가 "maintenance/ain 관련" 으로 이중 태깅되는 등 카테고리 오분류가 발생했다.
   수정: 3자 이하 키워드는 토큰 완전일치·텍스트는 단어 경계(`\b`) 매칭으로 전환(`kwHitTok`/`kwHitText` 헬퍼로 통일). 카테고리 2(차량 편의 및 보안)에 `hill`/`assist` 키워드 추가(`HillStartAssistControl_Control` 계열 인식 개선).
   실측 영향: 실제 Alogrithm.c 카테고리 분포가 수정 전/후로 유의미하게 바뀜 — 유지보수 3→5, 안전/Fail-Safe 8→10, 사양서 수록 함수 27→29. 오탐이 실제로 결과를 왜곡하고 있었다는 뜻이므로 수정 전 배포판을 그대로 뒀으면 안 됐다.

두 수정 모두 재적용 후 `node --check` 구문 검증 + 실제 `Alogrithm.c` 전체 파이프라인 재실행 + `docx` 생성 후 LibreOffice 변환까지 재확인(CRC 손상 없음, 정상 변환)했고, 브라우저에서 Phase 1(샘플 로드)→2(분석·상세·SVG 흐름도)→3(사양서 미리보기)→4(교차검증·다운로드) 전 구간 클릭 동작을 재확인했다.

## 회귀 버그 발견·수정 — `\b`가 밑줄을 못 넘는 문제

브라우저에서 샘플 코드로 재확인하던 중 `Power_Standard_Mode()`가 "동력 및 주행 제어"에서 "기타"로 잘못 밀려난 것을 화면에서 직접 봤다.

- 원인: 직전 회차에서 짧은 키워드(3자 이하) 오탐을 막으려 `kwHitText()`에 `\b키워드\b` 정규식을 넣었는데, JS 정규식의 `\b`는 `_`를 단어문자로 취급한다. `HCESPN.rpm_310`에서 `rpm` 뒤에 바로 `_310`이 붙어 있어 `rpm`→`_` 사이에 경계가 생기지 않아 `\brpm\b`가 매치 실패했다.
- 수정: 영문자 연속 구간만 뽑아 토큰화한 뒤 완전일치로 대조하는 방식으로 교체(`tokenize()`와 같은 철학).
- 실측 영향: 실제 `Alogrithm.c` 카테고리 분포가 동력/주행 12→14, 기타 5→3으로 회복. 브라우저에서 `Power_Standard_Mode()`가 다시 "동력 및 주행 제어"로 뜨는 것 확인.
- 배포 중 Pages 빌드가 같은 커밋에서 `built`/`errored`를 오가는 레이트리밋성 실패를 겪음 — 연속 수동 재트리거 대신 대기 후 자동 완료되는 것으로 해결(§4 "2~3분 간격 유지" 원칙과 동일 맥락).

## switch/case 개별 분기 세분화

기존엔 `switch` 전체가 다이아몬드 하나로 뭉뚱그려져 case별 로직이 안 보였다. 사용자 요청으로 세분화했다.

- `findCaseLabels()`: 중괄호 깊이 0에서만 `case`/`default` 라벨을 찾는다 — 중첩 switch/if 블록 안의 case 라벨이 바깥 switch로 잘못 섞이는 것을 막기 위함(단어 경계도 확인: `caseNumber` 같은 식별자를 `case`로 오인하지 않게).
- `scanSwitchBody()`: 찾은 라벨 경계로 본문을 잘라 각 구간을 `scanBlock()`으로 재귀 분석 — case 안의 중첩 if/return/switch도 정상 인식된다.
- 새 노드 타입 `{type:'case', cond:'라벨 또는 default'}` 를 `flattenBranches`(표 요약)·`pairBranches`(화면 SVG — "CASE 값:"/"DEFAULT:" 라벨의 개별 다이아몬드, 자기 자신의 하강 화살표엔 '예' 라벨 생략)·`flowToDocxParas`(Word — "▸ CASE 값:"/"▸ DEFAULT:") 세 군데 모두에 반영했다.
- **실제 `Alogrithm.c`로 검증**: `Check_Maintenance_Info()`의 `switch(request)`가 `case REQUEST_REPLACMENT_CONFIRMATION`·`case REQUEST_INTERVAL_CHANGE`로 정확히 분리되어 각자의 중첩 조건까지 정상 추출됨을 Node에서 직접 `flow` JSON을 찍어 확인. 화면 SVG는 well-formed XML 확인, Word 문서는 LibreOffice 변환 텍스트에서 "▸ CASE REQUEST_REPLACMENT_CONFIRMATION:" 등이 실제로 나오는 것을 확인(실 소스 3개 switch 전부 반영: 1857·1888·1920행).
- 사소한 남은 것: 화면 SVG에서 SWITCH 다이아몬드 자체의 하강 화살표에는 여전히 '예' 라벨이 붙는다(케이스 다이아몬드 자신은 생략되도록 고쳤지만, 그 부모인 SWITCH 노드의 화살표까지는 손대지 않음) — 문구상 사소한 어색함으로 구조적 오류는 아니라 이번엔 남겨뒀다.
